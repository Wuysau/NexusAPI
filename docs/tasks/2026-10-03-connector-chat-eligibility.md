# Local connector Chat eligibility

## Existing behavior

The generic Channel API accepts the public `chat` and `embeddings` capabilities, while connector creation stores historical transport values `text` and `streaming`. The connector snapshot replaces all saved capabilities with fixed Chat transport capabilities. Live authorization and model readiness do not check the saved capability selection.

An ignored real PostgreSQL/private-TLS Gateway/CLI characterization shows PATCH `['embeddings']` succeeds, the resource reports those saved capabilities, but the signed bundle still grants Chat, the model remains listed and an actual Chat succeeds. Normal Chat, priority/weight, pause and explicit `chat` restoration controls pass. The characterization passes because it records current behavior; it is not a desired-policy failing test. Its dedicated fixture applies all twenty-eight migrations and performs two actual inferences (10.08 seconds).

Channel capabilities are existing routing constraints, not immutable adapter declarations. Respect that saved selection. [LiteLLM's model access](https://docs.litellm.ai/docs/proxy/model_access) separates what a caller can discover and invoke; apply that consistency principle to the existing Channel and live connector authorization rather than introducing another resource identity. NexusAPI's capability vocabulary and eligibility rule remain its own policy.

## Minimal scope

Use one fixed SQL predicate for connector Channels: an array containing `chat` or legacy `text` grants the current Chat eligibility. Unsupported-only capabilities, `streaming` alone, malformed values and empty arrays grant no Chat. Apply it to connector snapshot candidates, live call/model-list authorization and readiness projection. In particular, omit ineligible Channels instead of emitting an empty capability list, because the existing Go router treats an empty list as unrestricted.

New connector Channels may use the public `['chat']` vocabulary. Preserve historical rows; never restore a removed permission by rewriting them automatically. The generic PATCH contract stays unchanged, and explicit PATCH `['chat']` restores eligibility. Resource capabilities remain the saved facts; a connected but ineligible connector has no ready models and its Channel resource is pending with unknown health.

Keep the existing fixed Chat transport behavior for eligible connector Channels. This round implements Chat eligibility, not new streaming/tool/multimodal permissions or protocol fields. Preserve the current ordinary-channel routing behavior.
