# Recent authentication for connection revocation

## Existing contract and design

After the pairing/rotation round (`d51008f`), the connection revocation route still uses ordinary `requireContext` with `credential:disable`. Its PATCH and DELETE both permanently revoke the connection, invalidate identities and leases, delete outstanding pairing material and disable associated local connector Channels. Channel DELETE already uses `requireHighRiskContext` for the same capability. Temporary Channel pause remains an ordinary reversible update.

Apply the existing fifteen-minute recent-auth guard to connection PATCH/DELETE before any transaction. Preserve current visibility, capability, CSRF, locking, audit and runtime revocation semantics. This follows [Nextcloud's server password-confirmation middleware](https://github.com/nextcloud/server/blob/v31.0.0/lib/private/AppFramework/Middleware/Security/PasswordConfirmationMiddleware.php) and [pending-action wrapper](https://github.com/nextcloud-libraries/nextcloud-password-confirmation): sensitive server operations enforce recent verification, while the UI can resume the original action. NexusAPI keeps its existing session rotation and policy rather than adopting a foreign timeout or dependency.

The existing connection confirmation dialog directly sends DELETE. Reuse the shared high-risk action and authentication dialog in an isolated confirmation component keyed by connection ID. Retain the selected ID; a canceled or removed confirmation must not resume its old action. The component owns its request cancellation and errors, so unrelated connection creation/project binding keeps its existing workflow. Closing a UI cannot roll back a mutation already accepted by the server.

## Characterization and verification

First prove the current server accepts PATCH/DELETE from a valid sixteen-minute session, and demonstrate the actual old UI lacks the required reauthentication after the backend repair. Extend the committed recent-auth native and browser fixtures; keep their existing pairing scenarios.

Native fixture ownership is the exact guarded query/fragment-free loopback port `55439` database `connector_test_reauth_round54` (or verified existing serial CI `convergence_ci15`). Browser ownership stays separate at `connector_test_reauth_browser_round54`. Prove `current_database()` before each schema reset and apply all twenty-eight canonical migrations. No private application environment files, subscription authentication or production databases are read.

Cover stale denials before business/success-audit changes, fresh and actual reauthenticated revocation, runtime credential invalidation, and existing capability/CSRF/visibility controls. Browser checks cover cancellation, a single retry for the original connection, fresh revocation and held real authentication responses after confirmation removal/replacement. Delay actual response delivery for lifecycle controls without stubbing authorization or relaxing CSP. Preserve real Gateway/CLI end-to-end revocation coverage and current unknown/unpriced accounting semantics.

Root owns production/UI/docs/Git and final validation. Delegated work owns only the existing native/browser fixture extensions and their separate ignored artifacts. No migration, Go change, deployment change or new authorization policy is planned.
