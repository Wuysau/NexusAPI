# Authenticated model lists for local credentials

Status: Accepted

The local console can register several models on one BYOK channel. The original `nexus.local-credential.v1` encrypted envelope binds exactly one model, so advertising additional channel models does not authorize the gateway to use that credential for them. Removing the model check would weaken the credential boundary.

Introduce `nexus.local-credential.v2` for newly saved and rotated local channels. Its AES-256-GCM additional authenticated data is the existing ordered array `[format, tenant_id, credential_id, credential_version, provider_id, base_url, protocol, model]` followed by `models` as one array element. `models` contains 1–50 unique, normalized model IDs; its first entry equals the retained primary `model`. The complete ordered list is authenticated. The gateway accepts a requested model only when present in that authenticated list. Tenant, provider, version, endpoint and protocol checks remain unchanged, as do grant expiry and per-write authorization. Production Vault credentials are unaffected.

Readers retain v1 compatibility and its exact single-model authorization. A v1 envelope with an added model list is rejected. Local primary-model diagnostics may read a legacy file when channel metadata lists more models; this never expands the gateway grant. Unknown versions, modified lists and invalid model identifiers fail closed. Old gateway binaries cannot read v2, so deploy a compatible gateway before enrolling v2 credentials. Existing signed snapshots already carry requested model IDs and credential versions; no snapshot schema change is necessary.

Upgrade is explicit, not an automatic consequence of seeing more models in a snapshot. `upgradeLocalChannelCredentialModels(ctx, channelId, expectedVersion)` in `src/lib/channels/local-management.ts` is a server-local repair entry point for an already authorized administrator. It accepts no replacement key, endpoint or model list. The caller provides the existing tenant/organization/user context and the version it reviewed. Do not expose it through an unauthenticated script or HTTP endpoint.

The repair locks the tenant/organization-scoped channel and provider credential together, checks the expected version, and requires the on-disk encrypted envelope to exactly equal the database envelope. It verifies and decrypts that envelope against the existing tenant, credential ID, version, provider, normalized endpoint, protocol and primary model. Only the validated, already saved `metadata.models` is enrolled. It publishes a new immutable version, then updates database pointers with additional envelope/version compare-and-swap conditions in the same transaction. A failed pre-commit operation rolls back and deletes only a new file successfully published by this invocation. After commit, the old file is removed and a metadata-only audit event is recorded. A v2 or single-model credential is verified and returned unchanged. Secrets never enter the return value or audit record; JavaScript plaintext exists only transiently in process memory.

Back up the scoped database record and host-private credential store before an operational repair. Reload the signed snapshot after successful repair. If interrupted before commit, an orphan next-version file causes a later publication to fail closed; inspect it before retrying. If interrupted after commit, inspect the committed version before any rollback or cleanup. The repair does not alter model configuration, provider, channel enablement, credential fingerprint, connection identity or financial history.

Regression coverage includes TypeScript encryption and file binding, an independent Go allowlist test, TypeScript-produced v1/v2 cross-language vectors, tampered/out-of-list rejection, and transaction mocks for stale versions, failed publication, guarded-update rollback and idempotent v2 checks. Live credentials are not fixtures.
